# Vibe Coding 成功要素全景图

从 0 到上线，一个项目成功的完整检查清单。

---

## 一、先搞清楚"做成什么样"

| 要素 | 问题 | 不搞清楚的后果 |
|------|------|----------------|
| 目标用户 | 谁用？解决什么问题？ | 做出来没人用 |
| 核心价值 | 用户为什么选你而不是别的？ | 功能堆了一堆，没一个好用 |
| 成功标准 | 怎么算"做完了"？可量化的指标？ | 永远在"再改改"，永远不上线 |
| MVP 范围 | 第一版只做什么？不做什么？ | 贪多嚼不烂，半年还没发布 |

---

## 二、技术选型（开写之前定死）

| 要素 | 说明 |
|------|------|
| 语言/框架 | TypeScript? Python? 选你最熟的，别追新 |
| 数据存储 | 文件？SQLite？PostgreSQL？跟数据量和并发匹配 |
| 部署方式 | 本地跑？Docker？Serverless？决定架构复杂度 |
| 第三方依赖 | 哪些用现成的（LLM API、飞书 SDK），哪些自己写 |

---

## 三、必须写的东西（代码之外）

### 1. 需求文档（最重要）

- 用户故事：作为 X，我要 Y，这样 Z
- 功能清单：每个功能一句话描述
- 优先级：P0（必须有）/ P1（应该有）/ P2（可以没有）
- 边界：明确不做什么

### 2. 数据模型

- 核心实体有哪些？字段是什么？
- 实体之间的关系？
- 状态有哪些？流转规则？

### 3. 接口设计

- 对外暴露什么 API / CLI 命令？
- 输入输出格式？
- 错误码定义？

### 4. 配置方案

- 哪些参数可配置？
- 配置文件格式？
- 默认值是什么？

---

## 四、代码层面必须有的东西

### 基础设施（不做就等着翻车）

| 组件 | 没有的后果 |
|------|-----------|
| 日志 | 出了 bug 不知道发生了什么 |
| 错误处理 | 一个异常整个程序崩溃 |
| 输入校验 | 用户传个 null 就炸 |
| 配置管理 | 改个参数要改代码重新部署 |
| 重试机制 | 网络抖一下就失败 |

### 可靠性（用户量上来就崩）

| 组件 | 没有的后果 |
|------|-----------|
| 限流 | 被第三方 API 封号 |
| 熔断 | 一个服务挂了拖垮全部 |
| 超时控制 | 请求卡死，资源耗尽 |
| 优雅退出 | 数据写一半，状态不一致 |

### 可观测性（出了问题找不到原因）

| 组件 | 没有的后果 |
|------|-----------|
| 结构化日志 | grep 都 grep 不出来 |
| 运行历史 | 不知道上次跑了什么、成功没有 |
| 健康检查 | 不知道系统是否正常 |
| 告警 | 出了问题用户先发现，你后知道 |

### 安全（不考虑就等着出事）

| 组件 | 没有的后果 |
|------|-----------|
| 认证授权 | 任何人都能操作 |
| 敏感数据保护 | API key 明文存储 |
| 输入安全 | 注入攻击 |

## 五、AI 生成代码的特有坑

这些不是传统开发的坑，是 vibe coding 才会踩的：

| 坑 | 表现 | 怎么防 |
|----|------|--------|
| **过度设计** | AI 喜欢加"以防万一"的抽象、接口、工厂模式 | 每次生成后问：这段代码删掉会怎样？能删就删 |
| **看起来能跑但逻辑错** | 代码不报错，但业务逻辑是错的（边界条件、状态流转） | 必须手动走一遍 happy path + 至少一个异常路径 |
| **一致性问题** | 模块 A 和模块 B 对同一个概念的理解不一样（字段名、状态枚举） | 先定义数据模型，所有模块共用，不要各自定义 |
| **忽略非功能需求** | 生成的代码没有日志、没有错误处理、没有超时 | 把"必须有日志和错误处理"写进 prompt 或检查清单 |
| **盲目信任生成结果** | "AI 写的应该没问题" | 每段生成的代码都要 review，至少扫一眼关键逻辑 |
| **上下文丢失** | 对话太长后 AI 忘了之前的约定 | 关键决策写进文档/prompt，不要只靠对话记忆 |

## 六、开发流程

| 阶段 | 要做的事 | 常见坑 |
|------|----------|--------|
| 设计 | 先画架构图、定义接口 | 直接开写，写到一半发现架构不对 |
| 实现 | 一个模块一个模块做，每个做完验证 | 一口气写完，最后跑不通 |
| 测试 | 每个功能写测试 | "先不写测试，后面补"（永远不补） |
| 集成 | 模块拼起来跑 E2E | 单元都能跑，拼起来炸了 |
| 文档 | 边写边写文档 | 写完代码忘了当初为什么这么设计 |

**vibe coding 核心原则：生成一段 → 验证一段 → 再生成下一段。不要一口气全生成完。**

## 七、项目分层架构

```
┌─────────────────────────────────────────────────┐
│                   入口层                          │
│            CLI / API / Web / 定时任务              │
├─────────────────────────────────────────────────┤
│                 流程编排层                         │
│        串联业务模块，处理分支、异常、补偿           │
├─────────────────────────────────────────────────┤
│                   业务逻辑层                       │
│  领域模型 │ 状态机 │ 业务规则 │ 策略 │ 事件        │
├─────────────────────────────────────────────────┤
│                   模块层                          │
│        按业务域拆分的独立模块                       │
├─────────────────────────────────────────────────┤
│                 可靠性 & 基础设施                  │
│  熔断器 │ 限流器 │ 缓存 │ 重试 │ 锁 │ 队列        │
├─────────────────────────────────────────────────┤
│                   适配器层                        │
│  外部服务抽象：数据库 / 第三方 API / 消息队列       │
├─────────────────────────────────────────────────┤
│                 可观测性                          │
│  日志 │ 指标 │ 运行历史 │ 健康检查 │ 告警          │
├─────────────────────────────────────────────────┤
│                 配置 & 安全                       │
│  配置文件 │ 环境变量 │ 敏感数据 │ 输入校验         │
└─────────────────────────────────────────────────┘
```

---

## 八、一句话总结

**vibe coding 成功 = 需求清晰 + 架构合理 + 基础设施不偷懒 + 每一步都验证。**

代码只是最后一环。前面的需求、设计、数据模型，比代码本身重要 10 倍。
